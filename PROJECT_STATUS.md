## Completed

- **Pre-UAT Hardening P1 — Safe Staging + Seeder Integrity:** The first slice of the Production Readiness + UAT architecture review's punch list, scoped narrowly to what a shared/staging environment needed before it could be safely exposed. `DatabaseSeeder` no longer creates any user account -- it now runs only the 8 idempotent configuration/reference seeders (roles/permissions, grades, positions, staff categories, academic year/periods, English programmes, learning phases), none of which touch `users`. The removed `admin@rahai.sch.id` / literal-`'password'` `super_admin` -- previously created unconditionally, in every environment, on every `db:seed` run -- is replaced by `php artisan rsms:bootstrap-admin`, a new Artisan command that creates a `super_admin` ONLY when both `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` are explicitly configured (`config/services.php`'s new `bootstrap_admin` block, read from config rather than a raw `env()` call so it still resolves correctly after `config:cache`). No predictable fallback exists at any layer -- absence of either credential is a hard refusal, not a default. Re-running the command is safe (an existing account by that email is left alone; the role is granted only if missing), and the password is never echoed, logged, or written anywhere -- it passes straight through `User`'s existing `hashed` cast. Two new top-level docs: [DEPLOYMENT.md](DEPLOYMENT.md) (staging environment checklist, an explicit Hostinger-unknowns checklist marked `TO VERIFY ON HOSTINGER` rather than guessed at, the permanent database-safety convention extended across all environments, and backup-timing requirements scoped by stage) and [UAT_ISSUE_TEMPLATE.md](UAT_ISSUE_TEMPLATE.md) (a plain Markdown issue-report template with the review's severity definitions, not an in-app feature). No migration.
- **Foundation F3.1 — Student Authorization Effective-Enrollment Patch:** A narrow, non-migration authorization-integrity patch discovered and flagged at F3's own closeout. `StudentPolicy::teaches()` (the sole method a teacher's `view($student)` check delegates to) queried the Student's `class_student` row and the Staff's `class_teacher` row with no effective-dating filter on either side, so a transferred-out/withdrawn historical enrollment, or a closed/handed-over teaching assignment, could both still grant a teacher current `view` access. Fixed in place with two independent open-row checks (`wherePivotNull('ended_on')` on the Student's own enrollment, `whereNull('class_teacher.ended_on')` inside the nested `teachers` `whereHas`) -- no new authority source, no migration (both columns already existed from F2/F3), and deliberately NOT widened to `TeacherAudienceScope`'s broader ClassSubject/TeachingGroup-inclusive definition, per existing `AcademicRecordPolicy`/`CommunicationPolicy` docblock evidence that `StudentPolicy`'s narrower homeroom/assistant-only scope is intentional, not an oversight. `StudentPolicy` grants no TeachingGroup or ClassSubject authority today, so there was nothing of that kind to preserve. A related-but-distinct gap was found during the same re-inspection and deliberately left unfixed as out of this patch's narrow scope: `Student::scopeTaughtBy()` still has no filter on the Student's own `class_student.ended_on` (see Technical Debt).
- **Foundation F3 — ClassStudent Effective Dating + Date-Aware Roster Integrity:** Third and final approved piece of the Foundation Integrity Pass. `class_student` gained `ended_on`, using a deliberately HALF-OPEN `[enrolled_at, ended_on)` boundary convention -- unlike `class_subject`/`teaching_group_student`'s closed interval -- specifically because a transfer closes and opens on the SAME calendar date; a closed interval would double-count the Student on that date. `class_student_current_enrollment_unique`, a partial unique index on `student_id` (not scoped by class), makes more than one open enrollment per Student a database-level impossibility. `ClassStudentService` (`enroll()`/`transfer()`/`withdraw()`/`correctCurrentEnrollment()`) is the one write path; the last is a tightly bounded same-day-only hard-delete correction, not a generic dependency-detection engine. `Student::currentClass()` resolves the open row directly and fails loud on corruption; `Student::classOn($date)` is the new historical helper. `ClassSubject::rosterOn()` is now genuinely date-aware for class-backed rosters too (previously teaching-group-only), so `Assessment::scoreSheetStudents()` inherited a correct, date-honoring roster with no code change of its own. `Attendance\Take`/`Report` both became date-aware (point-in-time and range-overlap respectively), fixing a real bug where a transferred-out student's historical attendance silently vanished from reports. `StudentGradeResolver::gradeOn()` was rewritten to resolve via `classOn($date)` rather than today's enrollment, fixing a genuine backdating correctness gap. `AcademicRecordService::resolveClass()` stays deliberately current-only (reviewed, reconfirmed, not changed); `ReportCardBuilder::classParticipation()` stays deliberately unchanged (reviewed, found already correct). `TeacherAudienceScope::authorizedStudentIds()` now requires an open row too. UI: Enroll/Transfer/Withdraw as three distinct actions, `unenrollStudent()`'s old hard `detach()` removed entirely; `Classes\Show` and `Students\Show` share one `ClassStudentService` lifecycle. No new permission. `ClassStudent` is now `Auditable`.
- **Foundation F2 — ClassTeacher Effective Dating:** Second approved piece of the Foundation Integrity Pass. `class_teacher` gained `started_on`/`ended_on` the same shape as `class_subject`/`teaching_group_student`, backfilled from the owning Class's `AcademicYear.start_date` (not invented history). Two partial unique indexes: `class_teacher_homeroom_open_unique` (at most one open homeroom row per class -- the actual singleton invariant) and `class_teacher_open_unique` (at most one open row per class+staff+role generally, replacing the old flat unique which would have blocked legitimate rejoin history). `subject_teacher` is deprecated for new writes -- an approved product decision, enforced structurally (`ClassTeacherService` exposes no method that accepts an arbitrary role) rather than by a runtime guard; existing rows are preserved, unmigrated, non-authoritative. `ClassTeacherService::setHomeroom()` is the one write path for homeroom: transactional close-and-create, idempotent, never a hard delete. `SchoolClass::homeroomTeacher()` now resolves only open rows and fails loud on corruption rather than guessing. `TeacherAudienceScope` and `AttendancePolicy::hasClassAccess()` both now require an open `class_teacher` row -- fixed together, in the same commit, so a handover cannot close one authorization surface while leaving the other stale. The date-order CHECK constraint (`ended_on >= started_on`) is PostgreSQL-only (SQLite's `ALTER TABLE` cannot add it to an existing table), guarded by the service and tests on SQLite instead -- a documented asymmetry, not a silent gap. No range-exclusion (overlap) constraint was added, per explicit instruction. `ClassTeacher` is now `Auditable`.
- **Foundation F1 — AcademicYear Current-State Integrity:** First approved piece of the Foundation Integrity Pass. `academic_years_current_unique`, a partial unique index on `(is_current) WHERE is_current = true`, makes more than one current Academic Year a database-level impossibility (Postgres and SQLite, identical syntax, same technique as `class_subject_active_unique`/`teaching_group_student_open_unique`). `AcademicYear::current()` is now fail-loud: still returns `null` when none is current (every existing caller already tolerated that), but throws `LogicException` rather than silently guessing if more than one row is ever found. `AcademicYearService::setCurrent()` is the one canonical write path -- one transaction, per-model updates (not a bulk query update, which would silently skip the `Auditable` trail), idempotent when called on the year that's already current. `AcademicYearSeeder` now calls it too, replacing its old non-transactional wipe-then-set. `AcademicYear` is now `Auditable`. A minimal "Change current Academic Year" panel was added to the existing `Classes\Index` page -- not a new admin module -- gated on `academic-years.manage` (an existing V1 Foundation permission, seeded and granted to `admin_staff` since the beginning but never actually checked anywhere until now). Explicit warning copy makes clear a current-year switch changes default scope only and is never a promotion, class rollover, enrollment transfer, or curriculum migration.
- **AI-Assisted Management (V9.0 / Phase V9A):** Provider-neutral infrastructure (`AiProvider` interface, DTOs, `FakeAiProvider` bound for every test, a real `AnthropicAiProvider` via Laravel's `Http` facade with zero new Composer dependency) plus two user-facing features: a Communication draft rewrite assistant, and a Daily Journal reflection assistant. AI never writes to a canonical model — structurally, not by convention: neither `CommunicationAssistant` nor `DailyJournalAssistant` holds a reference to its domain service, and each one's only output is a plain suggestion; applying it copies text into the Livewire component's unsaved form state, and saving still goes through the same unmodified domain-service method a manual edit already uses. Authorization is double-gated the same way V7A/V8A already scope teachers: the coarse `ai.use` kill-switch (granted to `principal`/`teacher`, withheld from `management`/`admin_staff`) unlocks nothing by itself — each assistant independently re-checks the exact policy gate a manual edit requires. `ai_generations` is metadata-only by explicit design (tokens, status, error code — no prompt, response, request payload or cost column), pinned directly by a schema test. Data sent to the provider is minimized to the draft's own content and settings — never audience rules, recipient identity, resolved logins, linked-record identity, or any student/guardian/staff name, proven against real named fixtures. The user's own text is always delimited and explicitly marked "never an instruction to you" in the system prompt, defending against injected text. Rate limiting (5/minute, 50/day, shared across both assistants) refuses before the provider is ever called; a rate-limited attempt is logged but excluded from its own daily count, so it cannot erode the user's allowance. Synchronous only, bounded timeout, no retries, no queue — a timeout, provider error, empty response, or unconfigured API key all degrade to the same plain "AI assistance is temporarily unavailable" message, never a crash.
- **Deterministic Management Insights + AI Narrative (V9A-5):** The fourth AI feature, and the first one where AI has NO data-discovery role at all -- seven deterministic providers (`ManagementInsightRegistry`) compute facts live from real records against an explicit `ManagementInsightScope` DTO, and an optional AI narrative only paraphrases the already-computed insights it receives, never queries the database, never sees student/staff/guardian names, ratings, evidence content, financial amounts, or record IDs. The v1 catalog is deliberately narrow: (A) active teaching assignments missing a Semester Programme, (B) Draft Teaching Modules on active assignments, (C) Draft Daily Journals, (D) Draft Performance Evaluations (administrative status count only, never ratings/evidence), (E) Published Communications with zero RSMS-reachable recipients (V8A semantics, never described as "failed delivery"), (F) active Staff with no `staff_category_id`, (G) active Students without a Published `AcademicRecord` for a completed Academic Period (student population derived from `students.status = 'active'` directly, deliberately NOT joined through `class_student` to sidestep Foundation Technical Debt). Explicitly EXCLUDED, and the absence itself is asserted by a structural test: no `class_teacher`-based provider (live incomplete-handover defect), no standalone `class_student`-chronology provider, no Assessment-missing-results provider (transitively depends on `class_student`), no Finance provider. Reliability is a three-state DTO field (`reliable`/`limited`/`unavailable`) enforced structurally -- when a fact is `unavailable`, the DTO's `count` MUST be `null` (`ManagementInsight`'s constructor throws otherwise), so "unknown ≠ zero" is a type-level guarantee, not merely a convention. `AcademicYear::current()` is deliberately NEVER called inside a provider; the Livewire dashboard resolves the year/period once at the UI boundary and passes an explicit scope down. `ManagementNarrativeAssistant` has no reference to `ManagementInsightService`, any provider, or any Eloquent model at all; its context is stripped to a strict six-field allowlist (`key`, `category`, `title`, `description`, `count`, `reliability`) by `ManagementNarrativeContextBuilder`. `management-insights.view` is a new dedicated permission (granted to `principal` and `management`); AI narrative additionally requires `ai.use`. The `management` role now holds `ai.use` for the first time -- narrowly, and only meaningful in combination with `management-insights.view`, since this role holds no write-side gates anywhere. `accepted_at` stays permanently `NULL` for `management_insight_summary` (no Apply step exists to accept). Empty-state protection disables the Generate button when every insight's count is `0` or unavailable. No new migration; no snapshot table; no cache; live computation per request.
- **Teaching Module AI Planning Assistant (V9A-4):** The third AI feature, extending V9A-3's structured-output pattern from two fields to five: `TeachingModuleSuggestion` (`plannedActivity`/`teachingStrategy`/`resources`/`differentiation`/`plannedAssessment`) — never `title`/`topic`/`teacher_notes`, and never capable of representing a Learning Objective link, a Semester Programme link, or curriculum/subject/roster identity. Generation requires at least one canonical Learning Objective (TP) already linked — mirroring `TeachingModuleService::markReady()`'s own ≥1-objective requirement rather than inventing a new rule — so the assistant always has a real pedagogical anchor and cannot select, replace, remove, or invent one; the AI writes *around* the TP, never *of* it. The draft-only firewall is load-bearing for a different reason than Daily Journal's: `TeachingModulePolicy::update()` has no closed-assignment branch at all (unlike Daily Journal, `TeachingModuleService::create()` has no backfill parameter — a plan can never be written against closed history, by anyone), but `update()` does legitimately allow editing a **Ready** module's `teacher_notes` while its five plan fields stay frozen — so `TeachingModuleAssistant::authorize()` still explicitly re-checks `isDraft()`, pinned by a test that first proves the policy would allow the Ready-module edit, then proves AI refuses anyway. Context is minimized to subject, roster name, an optional canonical `proficiencyLabel` (teaching-group-backed modules only, e.g. "Green" — never invented for class-backed ones), title/topic, linked objective texts, and existing plan-field values — never full CP text, adjacent objectives, ATP/Prota/Prosem detail, or any student/guardian data; `TeachingModuleContextBuilder` never queries a `Student` row, and since `TeachingModule` has no relation to `Assessment` at all, the planned-assessment firewall is structurally free. The module's own already-persisted `teacher_notes` field is deliberately kept separate from a new transient `teacherNotesForAi` input, rather than repurposed as AI prompt state. Apply is per-field across all five fields plus Apply All. Notably, the role-permission intersection here differs from Daily Journal's: `principal` holds both `academics.plan` (the permission this policy checks) and `ai.use`, so — unlike the Journal case — a principal genuinely can use this assistant on any active-assignment draft module.
- **Daily Journal Reflection Assistant (V9A-3):** The second AI feature, and this project's first structured-output assistant — `DailyJournalSuggestion` (`?reflection`, `?followUp`) is parsed from a strict JSON response via `json_decode(..., flags: JSON_THROW_ON_ERROR)`, never a regex over prose; a missing, `null`, empty, or wrong-typed field is dropped rather than coerced, and if neither field is usable the assistant reports `'unusable'` to its caller without touching the persisted `ai_generations` row, which correctly still reads `'success'` (the provider transport genuinely responded — interpreting that response is the assistant's job, not the log's). Scope is deliberately narrower than Communication's: only `reflection`/`follow_up` may be AI-suggested, never `actual_activity` (the factual record of what happened, versus the teacher's own interpretive/prospective judgment) and never any identity/date/link field — `DailyJournalSuggestion` is structurally incapable of representing them. The finalized-state firewall is genuinely stricter than the underlying policy: `DailyJournalPolicy::update()` legitimately lets a manager holding `academics.manage` correct a **finalized** journal, but `DailyJournalAssistant::authorize()` refuses AI there regardless via an explicit, load-bearing `isDraft()` re-check — pinned by a test that first proves the policy *would* allow the manual update, then proves the assistant refuses anyway. Context is minimized to subject, roster name, topic, linked objective titles, and existing reflection/follow-up text — never student/guardian names, Assessment or Teaching Module identity/results, attendance, journal date, or conductor identity; `DailyJournalContextBuilder` never queries a `Student` row. Apply is per-field (`applyReflection()`/`applyFollowUp()`/`applyBoth()`), unlike Communication's single-field Apply; `accepted_at` means only that at least one suggested field was applied, with no per-field acceptance tracking. Language is `id`/`en` only — no bilingual mode, since a Journal reflection has exactly one reader. Empirically confirmed (not assumed) against the real seeded role grants: no current role holds `ai.use` + `academics.record` + `academics.manage` together, so in practice no role can invoke AI on a backfilled draft journal today — a pre-existing consequence of the permission grants, not a new restriction, and no Journal-specific role exception was added.
- **Communication (V8.0 / Phase V8A):** Communication content, Audience, Recipient, Notification and External Delivery kept as five deliberately separate concerns — never one generic messages table. Draft → published → archived, published immutable with the one exception of archiving. Audience Rules are typed rows (12 rule types, one explicit resolver each, no JSON filter); Publish resolves them fresh and writes deduplicated `communication_recipients` once — later Class/Group/Guardian/role/category changes never rewrite that history, proven by mutating each after publish. Canonical recipient identity (staff/guardian/student/direct user, exactly one, DB-enforced) is kept separate from the resolved login, using the same exact-match discipline V7A built. Live Audience Preview shows resolved/reachable/unreachable counts honestly — a zero-reachable Guardian audience still publishes, with an explicit warning, and is never worded as "sent" or "delivered." Laravel database Notifications are the badge only; `CommunicationRecipient.read_at` is the canonical "opened in RSMS" state. Teacher authorization is checked at both the policy and service layer independently, scoped to current Class/Teaching Group assignments only — the raw `communications.manage` permission never unlocks a school-wide audience. V8A is honestly in-app only: no email, no WhatsApp, no scheduled publishing, no attachments, no two-way conversation.
- **Staff Performance Evaluation (V7.0 / Phase V7A):** Staff Categories → Performance Framework (sections, indicators of 4 response types, rating scale) → Evaluation → finalized record. The governing rule, enforced structurally not just documented: **system evidence never sets or suggests a rating.** A closed, hardcoded registry of 8 evidence keys (module/journal/assessment counts, roster-plan existence, and audit-derived individual contribution) is recomputed **live** and shown as visually subordinate context; the human response is written by a single, separate service that accepts exactly one type-appropriate field per indicator. Finalization is one transaction that snapshots the header, every item, and every live evidence result, and the record becomes permanently immutable with **no correction, replacement or supersession path** — the unique index on staff+framework+exact period already forbids re-evaluating that same scope, and V7A provides no workflow to work around it. A later evaluation is legitimate only when it is a genuinely different period, framework or version. An archived framework does not block finalizing an evaluation already in flight, because structure froze at activation. Self-view of one's own finalized evaluation is a policy carve-out (not a permission), gated by the same exact-match login rule the audit-derived evidence uses — a shared login is refused rather than guessed at. `teacher`/`admin_staff` hold neither performance permission by deliberate, conservative grant.

## Known Issues / Gaps

- **No password-reset flow.** Accounts are admin-provisioned; there's no "forgot password" screen. Not a bug — just not built yet.
- **No admin UI for managing roles/permissions.** They're defined in `RolesAndPermissionsSeeder` only; changing them today means editing code and re-seeding, not clicking through a screen.

## Development Conventions

- **Verify lifecycle-protected curriculum or performance data in an isolated database, not the dev one.** Manual verification that has to activate or archive a Curriculum or Performance Framework, or finalize an Evaluation, leaves rows the lifecycle guard correctly refuses to delete. Cleaning those up with direct SQL worked once, but it must not become the routine: bypassing a guard for tidiness is how a guard stops being trusted. Use a throwaway verification database (the `rahai_sms_verify` pattern already used for fresh-install checks) whenever the verification itself needs to leave draft, or clean up using only legitimate service methods (delete-while-draft, archive) and accept small, clearly-named, inert residue otherwise.
- **A mass query-builder delete/update (`Model::where(...)->delete()`) fires no Eloquent model events** — the same gap already known for `attach()`/`detach()`/`sync()`, discovered again in Phase V7A when an ad-hoc cleanup script used it and silently bypassed a Performance Framework's own structure-frozen guards. `->get()->each->delete()` fires events correctly and is what every service in this codebase actually uses; only reach for the query-builder form when events are genuinely not wanted.
- **PHP's `===` on two arrays requires identical key order, not just identical key/value pairs.** Discovered in Phase V9A: a "canonical row unchanged" test captured `$before` from an in-memory, just-created model (`toArray()` follows insertion order) and compared it against `$model->fresh()->toArray()` (follows database column order) — every pair matched, but the assertion failed anyway because the orders differed. Fixed by capturing both sides of the comparison from the same "freshly fetched" code path. Applies to any future "assert model unchanged" test in this codebase.
- **Never combine `artisan migrate:fresh` with `--env=production` as a way to "point at a different database."** Attempted in Phase V9A while setting up an isolated verification database and immediately backgrounded on a confirmation prompt that never resolves non-interactively — `--env` loads a different `.env.*` file, not a different connection, and non-`local` environments require an interactive confirmation `migrate:fresh` will otherwise hang on. The dev database was untouched (the command never got past the prompt) but it was a genuine near-miss. The correct way to point one `artisan` invocation at a different database without touching `.env` at all is an inline env-var override on the command itself, e.g. `DB_DATABASE=rahai_verify php artisan migrate:fresh --seed`.
- **Re-run a seeder after editing it, even against the dev database.** `RolesAndPermissionsSeeder` gained `performance.view`/`performance.manage` mid-Phase-V7A, but the dev database wasn't re-seeded until a policy sanity check surfaced the gap — the permissions didn't exist and no role held them, despite the seeder file already listing them. `Permission::firstOrCreate` / `Role::syncPermissions` make the seeder idempotent and safe to re-run at any time; there is no reason to defer it.

## Important Architectural Decisions

- **Effective-dating conventions are not one-size-fits-all across this codebase, and copying an existing one without checking can introduce a bug.** `class_subject` and `teaching_group_student` both use a CLOSED interval (`ended_on` is the last valid day, inclusive). `class_student` (Foundation F3) deliberately uses a HALF-OPEN interval (`ended_on` is the first EXCLUDED day) instead, because its transfer operation closes and opens on the SAME calendar date -- under a closed interval that would put a Student on two classes' rosters simultaneously on the transfer date. The choice was made and documented explicitly (in the migration, the model, and here), not inherited by default. A real bug was caught and fixed during F3's own build because of this exact distinction: an early implementation used plain string `where()` comparisons against `date`-cast columns, which are stored with a spurious `00:00:00` time suffix on SQLite -- making `'2026-08-15 00:00:00' > '2026-08-15'` lexicographically TRUE and silently breaking the exclusive boundary. Every date-range comparison in this codebase must use `whereDate()` (or an equivalent date-truncating comparison), never a bare string `where()`, against a date-cast column.
- **"Adding effective dates without updating date-sensitive consumers is not a complete fix" -- stated as an explicit governing principle for Foundation F3, and it changed the actual scope of the pass.** Adding `class_student.ended_on` alone would have fixed nothing observable: `ClassSubject::rosterOn()`, `Attendance\Take`/`Report`, and `StudentGradeResolver::gradeOn()` all had their OWN hardcoded "always resolve against today" logic that needed separate, deliberate fixes to actually benefit from the new column. This is the reusable lesson: a schema change to support point-in-time queries is inert until every caller that currently hardcodes "now" is identified and individually decided on (fixed, or reviewed and deliberately left alone with a stated reason) -- `AcademicRecordService::resolveClass()` and `ReportCardBuilder::classParticipation()` are the two F3 example of the latter: reviewed, and correctly NOT changed, because their existing "current-only" or "any-row-that-year" intent was never blocked by missing dates in the first place.
- **"DB enforces at most one, service enforces exactly one" proved out a second time, in genuinely different shape.** `AcademicYear.is_current` (F1) is a single-column singleton across the whole table; `class_teacher`'s homeroom invariant (F2) is a singleton scoped PER CLASS (`class_teacher_homeroom_open_unique` on `class_id` alone, effective-dated via `ended_on IS NULL` rather than a boolean flag). Same governing idea, different mechanics each time — confirms the pattern generalizes rather than being a one-off fit for `AcademicYear`. `ClassTeacherService::setHomeroom()` is the write-side guarantee, the same shape as `AcademicYearService::setCurrent()`.
- **A write path can refuse a value STRUCTURALLY, by simply not accepting it, rather than by a runtime guard.** `ClassTeacherService` has no method that takes an arbitrary role — only `setHomeroom()`, `assignAssistant()`, `endHomeroom()`, `endAssignment()` — so `subject_teacher`'s deprecation for new writes needed no `if ($role === 'subject_teacher') throw` anywhere. This is a stronger guarantee than a runtime check (nothing to forget to call, nothing a future generic method could accidentally bypass), and the same "explicit builders over generic engines" instinct already used for `ManagementInsightRegistry`/`EvidenceRegistry`, applied here to a write path instead of a read-side registry.
- **Two authorization surfaces that read the same underlying fact must be fixed in the same commit, never one first.** Foundation F2's Communication (`TeacherAudienceScope`) and Attendance (`AttendancePolicy::hasClassAccess()`) both depended on `class_teacher`'s stale-row gap and were fixed together specifically so a homeroom handover could never leave one surface correct and the other still trusting a stale row — an inconsistency that would have been *worse* than the original bug, since it looks fixed from one angle while remaining broken from another.
- **A DB constraint that SQLite cannot express is a documented asymmetry, not a blocker.** `class_teacher`'s date-order CHECK (`ended_on >= started_on`) is real on PostgreSQL (`ALTER TABLE ... ADD CONSTRAINT`) and absent on SQLite (whose `ALTER TABLE` cannot add a CHECK constraint to an existing table) — covered there by `ClassTeacherService::endAssignment()`'s own validation plus tests instead. Documented explicitly in the migration and here, rather than silently shipping asymmetric protection and letting a future reader assume parity between the two drivers.
- **"DB enforces at most one, service enforces exactly one" is now a reusable pattern, first applied to `AcademicYear.is_current` (Foundation F1).** The partial unique index makes more than one current row impossible; `AcademicYearService::setCurrent()` is the only write path that can make zero current rows impossible too (it always closes-then-opens in one transaction), so neither invariant depends on the other layer alone.
- **A resolver's fail-loud guarantee belongs on the read side of an invariant, not only the write side.** `AcademicYear::current()` throws on more than one current row even though the DB constraint already makes that state unreachable through normal writes — because "structurally unreachable today" and "provably impossible to observe" are different guarantees, and the cheaper one (a `match` on a small collection) is worth having regardless. The same reasoning already governs `AcademicRecordService::resolveHomeroomTeacherName()` and `StudentGradeResolver`, both of which refuse ambiguity rather than trust an upstream constraint to have caught it.
- **"Unknown ≠ zero" is enforced at the DTO layer, not merely by convention.** `ManagementInsight`'s constructor throws `InvalidArgumentException` when `reliability = 'unavailable'` is paired with a non-null `count` -- the first place in this codebase where a data-honesty property is guaranteed at the type layer rather than by prompt discipline or reviewer vigilance. The same "structurally unrepresentable" pattern the four prior AI DTOs use for firewall properties, applied here to a property that matters equally for humans reading the deterministic dashboard and for an AI paraphrasing it (a paraphrase that turns `null` into "zero" is a lie either way).
- **The read-side "explicit builders over generic engines" pattern is now proven at the reporting layer too, not just for write-adjacent authorization concerns.** `ManagementInsightRegistry` follows the same closed-hardcoded-map shape as `EvidenceRegistry`/`AudienceResolver` -- one provider per key, no database-defined queries, no JSON DSL, no formula language. An eighth insight is a code change that adds a provider class and lists it in the registry, forcing review; a data-driven registry would let a query nobody vetted quietly show up on a management dashboard. The absence of specific providers (`class_teacher`, `class_student`, `finance`, etc.) is itself asserted by a structural test so a well-meaning future addition triggers a test failure rather than silently shipping.
- **AI can be genuinely useful without being given data-discovery authority.** V9A-5 is the first AI feature in this codebase where the AI *cannot* see raw records, IDs, or names of any kind -- the deterministic providers compute every fact, and the AI narrative only paraphrases a stripped six-field allowlist. This is a different architectural shape from the three prior AI features (which see the actual draft they're rewriting), and worth flagging as a pattern for future data-adjacent AI work: whenever a user-facing question can be decomposed into "compute facts" + "narrate facts," splitting those into two separately-authorized layers is cheaper and safer than letting a single AI do both.
- **A required-precondition check (not just an authorization check) can be the right load-bearing gate for an AI assistant, when it mirrors an existing domain invariant.** `TeachingModuleAssistant` refuses to generate without at least one linked Learning Objective — not because any policy requires it, but because `TeachingModuleService::markReady()` already refuses to promote a module without one. Reusing that exact invariant as the AI's own precondition keeps AI availability consistent with a rule this project already enforces, rather than inventing a new AI-specific one; it also structurally prevents the assistant from ever operating as a generic, curriculum-detached lesson-plan generator.
- **The same "AI firewall may be stricter than the reused policy" pattern generalizes across different underlying reasons, and each occurrence must be re-derived, not assumed.** Daily Journal's `isDraft()` re-check is load-bearing because the policy legitimately lets a manager *correct* a finalized row. Teaching Module's `isDraft()` re-check is load-bearing for a genuinely different reason: the policy legitimately lets a Ready module's `teacher_notes` be edited, but all five AI-suggested fields are exactly what freezes at Ready — so without the explicit check, Generate would be reachable but every one of its outputs would be inapplicable. Same conclusion (refuse outright), different mechanism each time.
- **Role-permission intersections that produce an AI-authorization gap in one assistant do not automatically recur in the next one, and must be checked empirically each time.** Daily Journal found that no seeded role holds `ai.use` + `academics.record` + `academics.manage` together, so no role can use AI on a backfilled draft. Teaching Module's relevant permission is `academics.plan`, not `academics.record` — and `principal` holds both `academics.plan` and `ai.use`, so a principal genuinely *can* use the Module assistant on any active-assignment draft. The lesson is not "assistants X and Y behave the same way here" — it's "check the actual seeded grants against the actual policy every time," since assuming continuity between two superficially similar assistants would have been wrong here.
- **An AI assistant's own authorization check may be STRICTER than the domain policy it reuses, and that is sometimes required, not merely defensive.** `DailyJournalPolicy::update()` genuinely permits a manager to correct a finalized journal; `DailyJournalAssistant` still refuses AI there via an explicit `isDraft()` check that does real work (unlike Communication's equivalent check, which is redundant with a policy that already forbids editing a non-draft). The lesson generalizes: when reusing an existing policy for a new, narrower purpose, re-derive what the policy actually allows in every state rather than assuming a existing "the same gate a manual edit requires" pattern is automatically sufficient.
- **A provider-transport result and an assistant-level interpretation result are two different questions, and the first V9A structured-output assistant keeps them as two different types.** `ai_generations.status` (via the unmodified `AiGenerationResult`) answers "did the provider respond"; `DailyJournalAssistantResult::status` answers "was the response usable," and the two can legitimately disagree (`success` + `'unusable'`) without any new column or schema change — interpretation lives entirely in the assistant, never in the shared transport-level DTO or the log.
- **AI never writes to a canonical model — structurally, not by convention.** `CommunicationAssistant` has no reference to `CommunicationService` and cannot call `update()`/`publish()`/`archive()`; its only possible output is a plain suggested string. Applying a suggestion is the caller's job, through the caller's own ordinary, unmodified save path — the same shape as V7A's "system evidence never sets a rating" and V6's "a draft stores no frozen values," reused a third time for a third kind of irreversible-action boundary.
- **Authorization for AI is double-gated, neither layer trusting the other alone — the same discipline already used for V7A/V8A teacher scope.** `ai.use` is a coarse kill-switch permission; `CommunicationAssistant::authorize()` independently re-checks the exact `CommunicationPolicy::update()` gate a manual edit already requires, rather than trusting the Livewire component's own authorization call alone or trusting `ai.use` to imply anything about a specific record.
- **`ai_generations` is metadata-only by explicit design, with no prompt/response/request-payload/cost column.** Mirrors `PROJECT_STATUS.md`'s existing "computed, not cached" and "no table added before its phase needs it" database principles: token counts answer the questions this phase actually needs answered (rate limiting, usage visibility); persisting full prompts/responses was judged an unjustified privacy and storage liability with no concrete requirement driving it, and dollar-cost estimation can be added later if a real need appears.
- **The AI provider is a one-method interface bound to a fake in every single test, globally, via `Tests\TestCase::setUp()`.** No test file has to remember to fake it — the real `AnthropicAiProvider` is the default binding in `AppServiceProvider`, and the base test case's `instance()` override reliably wins for the whole suite because it runs after the provider is already registered. This is the structural guarantee behind "never a real network call in the automated test suite," not a per-test discipline that could be forgotten.
- **A rate-limited attempt is still logged, but explicitly excluded from the count that produces further rate-limiting.** `AiGenerationService::tooManyToday()` filters to `status IN ('success', 'failed')`, deliberately omitting `rate_limited` rows — otherwise a user who trips the 5/minute limit repeatedly would erode their own 50/day allowance for requests the provider was never actually asked to attempt.
- **System evidence and human ratings are written by entirely different services, and neither reads the other.** `EvidenceService` (evidence) and `PerformanceEvaluationItemService::respond()` (ratings) are the structural enforcement of "system evidence never sets a rating" — not a comment, not a code-review rule. No method anywhere resembles `autoRateIndicator()` or `calculateRubricFromEvidence()`, and a reviewer can verify the rule by checking that these two services never call into each other.
- **The Evidence Registry is a closed, hardcoded PHP list of 8 keys, not a database table or JSON configuration** — the same reasoning that kept Phase 6A's document generation to explicit builders rather than a generic engine. A ninth evidence source is a code change requiring a real provider class, which forces review; a data-driven registry would let an indicator quietly reference a query nobody vetted.
- **"Available at zero" and "unavailable" are never the same value.** `EvidenceAvailability` is a first-class enum returned by every provider, never inferred from `null` or `0`. A teacher with genuinely no modules yet and a teacher whose evidence cannot be attributed at all must render differently, or the UI would silently imply "did nothing" for "cannot tell."
- **The exact-match "never `first()`" rule for `staff.user_id` (documented as Technical Debt below) is reused for two different purposes in Phase V7A**, both via one shared trait (`App\Models\Concerns\ResolvesUnambiguousUser`): deciding whether audit-derived contribution evidence can be attributed to a staff member, and deciding whether a logged-in user may self-view their own finalized evaluation. A login shared by more than one Staff row is refused in both directions rather than guessed at.
- **A Performance Evaluation auto-provisions one item per framework indicator at creation, rather than letting a caller choose indicators ad hoc.** This eliminates the "does this item's indicator actually belong to this evaluation's framework" bug class by construction: an item only ever exists for an indicator that was on the framework when the evaluation was created, and framework structure is frozen the moment it activates.
- **Finalization reuses Phase 6A's snapshot-at-the-moment-of-the-irreversible-action pattern.** A draft evaluation stores no frozen values and its preview reads live data every time, exactly like a draft Academic Record; `finalize()` re-reads everything live and writes snapshot columns atomically, exactly like `publish()`. The two features share no code, but they share the same shape deliberately.
- **Finalized is immutable with no correction, replacement or supersession path in V7A, by deliberate choice, not oversight.** Unlike Academic Records (which supersede deliberately), a Performance Evaluation's unique index on staff+framework+exact period already forbids re-evaluating that exact scope, and V7A adds no workaround for it — a mistaken finalized record simply stays as it is; the original is never rewritten or deleted. A later evaluation is legitimate only when it represents a genuinely different period, framework or version. A supersession/correction workflow was judged premature with no concrete Rahai requirement driving its shape yet; if one is needed, it will be designed as its own feature (e.g. manager correction, or void/replacement).
- **Self-view is a policy carve-out, never a permission.** `PerformanceEvaluationPolicy::view()` grants a staff member their own finalized record independently of `performance.view`/`performance.manage`, so `teacher` and `admin_staff` can hold neither permission (a deliberately conservative grant) while self-view still works for them.
- **`class_subject` is the single Teaching Assignment store.** One row = one subject + one roster + one teacher + a date range, where the roster is an administrative class XOR a teaching group. No parallel `teaching_group_subject` table, and no rename of the physical table — `assessments.class_subject_id` and every other reference keep working, and the domain concept lives in the model's documentation rather than in churn.
- **Teachers author pathways, scoped by what they actually teach.** The `academics.plan` permission is not a blanket grant: a teacher may draft only where they hold an *active* teaching assignment whose subject and resolved scope match the pathway. Year 5 and Year 6 Mathematics teachers both resolve to Phase C and collaborate on one record, which is the point. Activation stays with management — that is the approval step, so no separate approval workflow was built.
- **Alternative pathways coexist; they are not versions.** Several may be active for one scope + subject, and activating one never retires another. This is the one place the curriculum layer deliberately does NOT copy the single-active rule used for objectives.
- **TP is the school's formulation, not the published standard, so it has its own lifecycle.** CP inherits the curriculum's state; TP carries draft/active/archived of its own, because educators write and revise objectives while a curriculum is in force. Requiring every TP before activation would have made activation punitive and pushed curricula to stay in draft forever — which would have made versioning decorative.
- **A learning objective's anchor is immutable from creation.** Not merely after activation: moving a Phase C objective to Phase D would re-point what it serves and unpick the composite keys binding its CP links. An unused draft in the wrong place is deleted and rewritten.
- **Published curriculum content is immutable; a change means a new version.** A shared model guard refuses edits to scopes and outcomes once their curriculum leaves draft — for managers too, because this is versioning rather than a permission question. Drafts stay fully editable.
- **Cross-table integrity is bought with one deliberate discriminator, not with triggers.** `curriculum_scopes.english_programme_id` exists so composite foreign keys can enforce that an English level belongs to the same programme as its curriculum — something no single-column constraint can express. The one direction NULL semantics leave uncoverable is stated as an application-level rule rather than assumed away.
- **A curriculum VERSION is a historical record, never a row that gets overwritten.** Identity is `code` + `version` and becomes immutable the moment a version leaves draft; superseding archives the old version and opens a new one. Work recorded under the 2025 standards must keep pointing at the 2025 standards.
- **Learning outcomes will belong to a Learning Phase, never to a grade.** Phase C covers Year 5 and Year 6 with one set of outcomes; grades resolve through `learning_phase_grade`. This is why phases are a table rather than an enum, and why `grades` carries no phase column.
- **A signed-in user is resolved to staff explicitly, never through the `HasOne`.** `staff.user_id` has no unique index, so `User::staff()` would silently pick one of several. Anything showing "my" work resolves candidates itself and refuses on zero or many, because guessing here means showing one teacher another teacher's students.
- **Report-card discovery is a union of results and participation.** Results answer "what happened" and survive every later change of membership, assignment or group status; participation answers "what should appear even with no marks yet". Deduplicated by assignment id, so no score is counted twice for being found by both paths.
- **Report-card rows are merged by subject, never by roster.** English taken in Green A then Blue A is one row with two period columns — the roster a student sat in is not a fact the report card reports on.
- **A score sheet is the roster on the day, union everyone already scored.** A recorded mark is historical evidence, so a student who leaves a teaching group keeps appearing on assessments they were scored on. The union is computed from `assessment_results` rather than snapshotted, so there is nothing to keep in sync. The same union is the write allowlist.
- **Roster accessors take a date.** `rosterOn($date)` rather than a bare "current roster", because an ambiguous accessor is how historical assessments silently lose students. ~~Group rosters honour the date; class rosters cannot, because `class_student` is not effective-dated~~ -- **as of Foundation F3, both roster sources genuinely honour the date.** `SchoolClass::studentsOn($date)` resolves class-backed rosters the same way `teaching_group_student` always resolved group ones; `Assessment::scoreSheetStudents()` inherited the fix with no code change of its own.
- **A teaching assignment's roster source is immutable.** Changing it would rewrite what every assessment hanging off the row was about, so the model throws; the supported answer is end-and-create, the same shape as never mutating `staff_id`.
- **Modular monolith**, not microservices — one Laravel app, one database, feature-organized folders.
- **Invoice balance/status is always computed**, never stored as a mutable field (`Invoice::balance()`, `Invoice::refreshStatus()`) — chosen specifically to prevent the finance ledger from ever drifting out of sync.
- **Policy-layer scoping, not just UI-hiding**, for teacher access (own classes/subjects only) — verified via direct-URL-access tests, not just "the button isn't shown."
- **Group membership and assessed proficiency are separate facts, never synchronised.** A student assessed Blue may legitimately still attend Green A. Recording a new level closes the old one and opens a new one; it does not touch group membership, because moving a student is a human decision that a re-assessment only informs.
- **Effective-date integrity lives in services, not constraints.** Grade eligibility, no-overlapping-membership (within a group and within a programme), and no-overlapping-proficiency all need either a date-range exclusion constraint (PostgreSQL-only; SQLite runs the test suite) or a join through `english_levels` that an index cannot see without copying `english_programme_id` onto every membership row. All are enforced in `app/Services/` inside a transaction that locks the student row first. Documented as application-level so nobody assumes the database is the backstop — verified directly: PostgreSQL does accept overlapping closed ranges.
- **A student's grade is resolved only through the existing class structure, and the resolver never guesses.** `StudentGradeResolver` is the single place that knows the path. ~~Where Phase 1's flat `class_student` allows a student two active classes in different grades in one year, it reports the ambiguity rather than picking one the way `Student::currentClass()` does.~~ Foundation F3 made that state a database-level impossibility for both resolvers (`class_student_current_enrollment_unique`); the ambiguity check remains as defense-in-depth, not because it is expected to fire. It likewise refuses to substitute the current academic year for a date that matches no configured year, or to pick between two overlapping years. `gradeOn($date)` was further sharpened in F3 to resolve the grade genuinely AS AT `$date` (via `Student::classOn($date)`) rather than today's enrollment -- needed because English-placement backdating can legitimately ask about a Student's grade on a past date after they've since transferred classes.
- **Proficiency levels are scoped per programme, never globally.** Rahai runs more than one English framework at once, so uniqueness on level name and sequence is `(programme, name)` and `(programme, sequence)` — "Level A" can legitimately exist in two frameworks. A grade maps to at most one programme (`UNIQUE(grade_id)`), enforced by the database rather than the UI.
- **Pivot writes go through a real model, never `attach()`/`sync()`.** Those methods operate through the query builder and fire no Eloquent events, so an `Auditable` pivot written that way silently records nothing. Verified empirically before relying on it; `EnglishProgrammeGrade` is a full model and its `belongsToMany` counterpart is marked read-only.
- **Academic periods are data, not constants.** `academic_periods` (Semester 1/2 for Rahai) replaced the hardcoded Term 1/2/3 vocabulary; the report card renders whatever periods a year defines, ordered by `sequence`. `assessments.term` is deprecated and unreferenced, pending a later drop migration.
- **Datalist over a JS combobox library** for the Staff position "type or pick" field — native HTML, zero new dependency.
- **Teaching assignments are effective-dated, never mutated.** Reassigning a subject closes the outgoing `class_subject` row and opens a new one, so anything referencing it (assessments today, Phase 5 planning records later) keeps identifying the teacher actually in force. Enforced by a partial unique index over active rows only, which works identically on PostgreSQL and SQLite.
- **Read/write split on historical assignments:** teachers keep read access to their own past work but cannot write to a closed assignment; admins retain write access for corrections.
